# Skill 与插件调用权重

目标不是提高 Skill 调用次数，而是提高任务结果。没有“每个任务至少调用几个 Skill”的指标，也不能因为通用模型能勉强完成，就永远忽略专业能力。

机器可读参数见 [capability-routing-policy.json](../plugins/codex-fullstack-workbench/assets/capability-routing-policy.json)。它是一套初始启发式，不是假装精确的质量预测；真实项目可以根据复盘调整阈值。

## 先过四个强制判断

以下情况优先于分数：

1. 用户明确点名可用 Skill：在请求范围内按该 Skill 执行。
2. 特定文件或平台有明显更高保真能力：例如 PDF、表格、Figma、Sentry、Supabase，使用匹配能力。
3. 权限、认证、迁移、部署或安全高风险任务：调用对应审查与验证能力，即使平时低频。
4. 安装、登录、外部写入、消息发送、发布、部署和迁移：无论收益多高，都先取得确认。

## 收益分：0–5 分后加权

| 维度 | 权重 | 0 分 | 5 分 |
| --- | ---: | --- | --- |
| 任务专业匹配 | 35% | 只重复通用常识 | 包含任务必需的专有流程或领域知识 |
| 质量与验证增益 | 25% | 输出和验证不会改善 | 能显著改善正确性、保真度或验收证据 |
| 风险降低 | 20% | 几乎没有风险差异 | 能阻止权限、数据、迁移、发布等高代价错误 |
| 确定性资源 | 10% | 只有泛化文字 | 提供可靠脚本、Schema、模板或工具调用 |
| 重复与杠杆 | 10% | 一次性任务 | 多步骤或跨项目反复复用 |

## 成本分：0–5 分后加权

| 维度 | 权重 | 0 分 | 5 分 |
| --- | ---: | --- | --- |
| Context 加载 | 40% | 元数据和指令极轻 | 主体庞大、引用多且会挤压实现上下文 |
| 权限、数据与网络 | 30% | 纯本地只读 | 需要登录、敏感数据、外部写入或付费调用 |
| 安装与维护 | 20% | 已可用且稳定 | 需要复杂安装、运行时和持续升级 |
| 重叠与触发冲突 | 10% | 能力边界清晰 | 与多个 Skill 重复且容易同时触发 |

计算方式：

```text
净收益 = 加权收益 - 0.6 × 加权成本
```

成本乘以 0.6，是因为 Context 和安装成本应该降低调用概率，但不能压过高风险任务的正确性收益。权限类动作仍由强制确认规则控制，不能靠高分越过。

## 阈值

| 净收益 | 行为 |
| ---: | --- |
| `≥ 2.0` | 使用该 Skill；插件已连接且在授权范围内时调用 |
| `1.0–1.99` | 条件式使用：已安装、低成本且边界清晰时使用；否则直接完成或作为可选建议 |
| `< 1.0` | 不加载，使用通用能力 |

默认一个实施切片只选 1 个主 Skill 和 1 个辅助 Skill。只有任务确实包含互不重叠的产物，例如“实现页面并生成正式 Excel 报告”，才增加能力。

## 典型例子

### 修改一个变量名

通用编辑能力已经足够。前端审美、架构或浏览器 Skill 的专业匹配和质量增益都很低，不调用。

### 实现响应式落地页

`frontend-quality` 在视觉层级、状态、移动端、可访问性和浏览器验证上都有明显增益，净收益高，应作为主 Skill。若已有 Figma 源，再把 Figma 作为辅助能力。

### 分析 PDF 合同

`document-ingest` 或 PDF 专业能力能保留来源、处理二进制格式并提醒转换失真，应使用。普通文本读取不能提供同等保真度。

### 项目没有接入 Sentry，却安装了 Sentry 插件

专业匹配低，认证与维护成本高，不调用。安装状态不是使用理由。

### 修改认证和跨租户权限

`database-auth` 与 `security-review` 分别承担实现和审查。即使两者不常用，风险降低足以超过 Context 成本；这是允许一个主 Skill 加一个辅助 Skill 的场景。

## 防止“完全不用 Skill”

- 在规划阶段检查能力地图，而不是只靠模型记忆。
- 遇到特定文件、平台、专业栈或高风险边界时，强制做一次匹配判断。
- 如果通用执行失败、重复返工或缺少验证，使用 `skill-lifecycle` 搜索或创建更合适能力。
- 交接时记录专业能力带来的真实增益；没有增益的能力降低优先级，不因一次失败永久删除。

## 防止“为了用而用”

- 不设置调用数量目标。
- 不同时启用整套 Profile。
- 不因名字相关就加载；必须能指出它改善哪项结果。
- 不把多个重叠工作框架、审美体系或浏览器工具叠在同一切片。
- 不在普通任务中展开评分过程；只有边界不清、需要安装或需要解释取舍时展示分数。

这套路由的最终要求是：该用时能解释具体增益，不用时也能解释为什么通用能力足够。
