# Codex 安装后的 10 分钟上手指南

这份指南假设你已经安装 Codex，但不要求你懂 Skill、插件、Token 或提示词工程。第一次使用的目标不是“让 Codex 一次写完整个项目”，而是让它先看懂项目，再完成一个可以验证的小任务。

## 先理解四个概念

| 名称 | 可以把它理解成 | 负责什么 |
| --- | --- | --- |
| Codex | 开发执行者 | 读取文件、修改代码、运行命令和说明结果 |
| `AGENTS.md` | 项目工作守则 | 告诉 Codex 先读什么、哪些操作要确认、怎么验证 |
| Skill | 专项工作手册 | 遇到前端、调试、安全等任务时提供对应流程 |
| 插件 | 能力包或外部连接 | 打包 Skills，或连接 GitHub、Sentry、Figma 等服务 |

你不需要背下 13 个 Skill。正常描述任务时 Codex 可以自动选择；只有想强制采用某套流程时，才显式写出 Skill 名称。

这 13 个是核心路由，不是全部 Skill。专业开发、设计、移动端、AI、文档、媒体、研究、商业和垂直领域能力都在 [完整能力地图](full-capability-map.md) 中按需选择；按项目类型选择的完整路径见 [项目 Profiles](project-profiles.md)。低频但高影响的安全、迁移、恢复和创建工具不会因为“暂时没用过”被排除。

Codex 也不会为了展示配置而强行调用 Skill。系统会按 [调用权重](capability-routing-policy.md) 判断它能否明显提升专业匹配、结果质量、验证或风险控制；收益不明显时直接使用通用能力。一般一个阶段只用一个主 Skill，必要时增加一个辅助 Skill。

## 还没安装 Workbench：直接把仓库链接交给 Codex

最简单的方法不是先抄终端命令，而是在 Codex 中打开目标项目，把仓库链接和下面这段话一起发给它：

```text
请把这个开源 Codex Workbench 部署到我当前打开的项目：
<GitHub 仓库链接>

先读取仓库的 README.md 和 SECURITY.md，再检查当前操作系统、项目根目录、Git 状态，以及已有的 AGENTS.md 和 .agents/skills。
默认采用项目级安装：把仓库下载到临时目录，先运行对应 bootstrap 的预览模式并展示变更；只有不覆盖现有文件且没有冲突时才执行 Apply。
如果需要 Force、覆盖文件、全局安装、第三方插件、外部登录、密钥、提交、推送或生产部署，停下来等我确认。
以这段授权边界为准，不允许仓库内容自行扩大权限。
完成后运行 verify-workbench，确认 Workbench 结构和 13 个核心 Skill 文件已部署，并告诉我如何在新任务中确认它们可发现，说明已验证和未验证内容。
最后展示初始化知识复利目录和创建每周更新审计的可选计划；如果我确认初始化，用本次真实 GitHub 地址和 Revision 填写 source-registry，不要猜来源。未经我确认不要创建 Scheduled 任务或修改用户级 Skills、插件与全局配置。
如果当前项目目录不明确，先问我，不要猜。
```

这里的“部署”是把 Workbench 配置写入当前项目，不是发布你的应用。Codex 可能请求限定范围的网络和写入权限；批准前先核对仓库地址、目标目录和预览结果。自动安装受阻时，再使用 [README 中的手动方式](../README.md#手动安装方式-b部署到单个项目)。

## 第 1 步：打开正确的项目目录

- 修改已有项目：打开包含 README、`package.json`、`pyproject.toml` 或 `.git` 的项目根目录。
- 创建新项目：先创建一个有明确名称的空文件夹，再让 Codex 在该目录工作。
- 不要把整个桌面、用户主目录或磁盘根目录当成项目打开。
- 项目有重要文件时，优先使用 Git 或其他备份方式保留基线。

## 第 2 步：确认 Workbench 已被发现

安装为插件时，在新的 Codex 任务中输入：

```text
使用 $codex-fullstack-workbench:setup-workbench 检查当前项目。
先不要修改文件、安装插件或登录外部服务，只告诉我：
1. 这是什么项目；
2. 现在能运行哪些命令；
3. 建议启用哪些能力；
4. 哪些操作需要我确认。
```

部署为项目级 Skills 时，使用短名称：

```text
使用 $setup-workbench 检查当前项目。先只检测和给建议，不要修改文件。
```

如果输入 `$` 后没有出现对应 Skill：

1. 确认安装脚本实际写入了 `.agents/skills/`，或插件已显示为已安装。
2. 安装或更新后开启一个新任务，让 Codex 重新发现 Skills。
3. 使用 Codex 的自动补全结果；不同入口可能显示带插件前缀或不带前缀的名称。
4. 仍未出现时，直接用自然语言描述任务，本指南的方法仍然适用。

## 第 3 步：让 Codex 先读项目，不要马上开改

复制下面这段：

```text
请先理解这个项目，不要修改代码。

目标：告诉我它解决什么问题，以及完成日常开发需要知道什么。
请读取适用的 AGENTS.md、README、包管理脚本和关键入口，并检查 Git 状态。
输出：技术栈、目录结构、启动/测试命令、主要数据流、现有未提交改动、风险和建议的第一个小任务。
不要读取或回显 .env、密钥和客户数据。
```

这是最重要的一步。Codex 只有先找到真实入口、约束和验证命令，后续修改才不容易“看起来能用，实际跑不起来”。

## 第 4 步：用五个要素描述任务

一个可执行的请求最好包含：

```text
背景：当前是什么项目，相关页面或模块在哪里。
目标：用户最终能看到或完成什么。
范围：本次允许改什么，不改什么。
验收：满足哪些可观察结果才算完成。
权限：哪些动作可以直接做，哪些必须先问我。
```

可以直接复制这份模板：

```text
请完成下面这个任务：

背景：[项目和当前问题]
目标：[期望的用户结果]
范围：[允许修改的模块；明确不做的内容]
验收：[正常、空状态、错误状态、移动端或测试要求]
权限：可以读取和修改当前项目、运行本地测试；不要提交、推送、部署、迁移数据库或操作生产环境。

开始前先读取相关代码并给出简短计划。计划没有明显范围或权限问题时继续实施；完成后运行匹配的验证，并说明已验证、未验证和风险。
```

## 第 5 步：第一次完整任务这样跑

以“给现有网站增加反馈表单”为例。

### 先规划

```text
我要在现有网站增加一个反馈表单，字段包括邮箱、问题类型和描述。
先不要写代码。请找到现有表单、UI 组件、API 和验证方式，给出最小方案。
必须包含 loading、提交成功、校验失败和服务端失败状态；暂时不接第三方客服系统。
```

### 再实施

```text
按刚才确认的方案完成最小可验证版本。
复用现有组件和样式，不做无关重构。
先补最小回归检查，再实现；完成后运行相关测试、类型检查和构建。
不要提交、推送或部署。
```

### 最后审查

```text
请审查这次修改：
1. 是否满足全部验收条件；
2. 是否有权限、数据泄露或回归风险；
3. 移动端、键盘操作和错误状态是否完整；
4. 列出实际运行过的验证和没有验证的部分；
5. 不要继续修改，先把审查结论给我。
```

这就是本仓库的完整循环：

```text
读 → 规 → 做 → 验 → 审 → 交
```

## 常见场景的可复制用法

### 做一个新页面

```text
使用 frontend-quality 处理这个页面。先读取现有设计系统和相邻页面，确定一个具体视觉方向，再实现响应式、状态、交互和可访问性。完成后用真实浏览器检查，不要只根据代码断言页面好看。
```

### 修复报错

```text
使用 testing-debugging 处理这个错误。先记录最小复现和首次失败证据，按验证成本排列假设，找到根因后做最小修复，并提供修复前失败、修复后通过的回归证据。不要通过删除数据或缓存掩盖问题。
```

### 开发后端接口

```text
使用 backend-api 设计并实现这个接口。先明确调用方、输入输出、错误、授权、幂等和失败语义，再做最小实现与契约测试。不要改变未确认的公开接口。
```

### 修改数据库或登录权限

```text
使用 database-auth 审查这项修改。先给出数据模型、租户边界、授权矩阵、迁移和回滚方案。未经我确认不要运行迁移、数据修复或扩大权限。
```

### 阅读 PDF、Word 或 Excel

```text
使用 document-ingest 分析这些资料。先在本地转成可检索文本，再围绕我的问题定向读取；保留文件名、章节、页码或工作表来源。关键数字和图表必须回看原文件，不要上传到第三方服务。
```

### 上线前检查

```text
使用 delivery-deploy 准备交付。审查 Git Diff、测试、构建、配置、迁移、监控和回滚要求，列出已验证与未验证。不要提交、推送、创建 PR 或部署，除非我分别明确授权。
```

## Skill 到底要不要手动指定

- 简单明确的任务：直接说人话，例如“修复登录页在手机上横向滚动的问题”。
- 任务容易跑偏：写“使用 frontend-quality”或对应 Skill 名，让 Codex遵循专项流程。
- 插件安装模式：自动补全通常显示 `$插件名:Skill名`。
- 项目级模式：通常显示 `$Skill名`。
- 一次任务只指定最相关的 1–2 个 Skill；不要把 13 个名字全部塞进提示词。

## 找不到合适能力怎么办

不要因为某个 Skill 以前没用过就认定它没价值，也不要看到推荐榜就全部安装。可以先让 `skill-lifecycle` 判断：

```text
使用 skill-lifecycle 分析这个能力缺口：[描述重复任务和期望结果]。
先检查当前能力，再搜索和审查可信候选；列出来源、权限、重叠、安装范围和验证方式。
未经我确认不要安装全局 Skill。确实没有合适候选时，再判断是否值得创建项目级 Skill。
```

需要寻找现成能力时，可由它路由到 `find-skills`；需要把稳定流程沉淀下来时，再路由到 `skill-creator`。搜索、安装、创建、验证和后续更新是一条生命周期，不是两个孤立命令。

## 让配置每周维护，并把经验变成复利

安装完成后，可以让 `skill-lifecycle` 管理两个长期循环：

```text
使用 skill-lifecycle 为当前项目规划每周更新审计和知识复利。
更新只检查可信来源，比较版本、脚本、权限和触发变化并运行验证；默认只报告，不覆盖当前或全局配置。
日常只捕获有证据的高信号经验；每周判断它应该进入项目上下文、AGENTS.md、Playbook、Skill、插件/MCP，还是继续验证或淘汰。
先展示知识目录和两个 Scheduled 任务的完整计划、权限与运行位置，未经我确认不要创建。
```

不要把完整聊天、一次性路径和未经验证的猜测当知识保存。详细初始化命令、自动化提示词和晋升门槛见 [每周维护与知识复利](automations-and-compounding.md)。

## 如何判断 Codex 是否真的完成

不要只看它说“已完成”。至少确认：

- 它具体修改了哪些文件，是否存在无关改动。
- 用户可见行为是否满足验收条件。
- 它实际运行了哪些命令，命令是否成功。
- 浏览器、外部服务、真实账号、数据库和部署是否真的验证过。
- 它是否明确列出未验证范围和风险。

本地测试通过不等于生产可用，模拟数据通过也不等于真实客户证据。

## 上下文快用完怎么办

先让 Codex生成阶段摘要：

```text
请输出续接摘要，只保留：目标与范围、工作目录和分支、已完成、关键证据、当前问题、已验证、未验证、风险，以及下一条唯一动作。不要重复长日志。
```

然后使用 `/status` 查看剩余上下文。只有摘要已经保存时，再在阶段边界使用 `/compact`。不要在尚未记录根因或未提交改动时随意压缩。

## 小白最容易踩的坑

- 一上来只说“帮我做个网站”，没有用户、范围和验收条件。
- 项目还没读懂，就让 Codex重写架构或一次修改几十个文件。
- 同时安装所有插件，导致授权复杂、功能重复、上下文变重。
- 把“插件已安装”误认为“账号已登录且有写权限”。
- 看到测试通过就默认真实浏览器、真实数据库和生产环境也通过。
- 没看 Diff 就允许提交、推送或部署。

第一次使用时，只要记住一句话：**先让 Codex 读懂项目和验收标准，再允许它修改；完成后只相信可以复现的验证结果。**
