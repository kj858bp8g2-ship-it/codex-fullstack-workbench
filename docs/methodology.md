# 工作方法：读 → 规 → 做 → 验 → 审 → 交

## 1. 读

先定位适用的 `AGENTS.md`、README、包管理脚本、关键入口和当前 Git 状态。使用 `rg` 或文件清单定向读取，不做无目的全仓库遍历。

## 2. 规

明确成功标准、范围边界、停止条件、验证方式和需要用户确认的高风险操作。公开接口、数据库迁移、权限与部署变化必须显式指出。

## 3. 做

实施最小可验证切片，优先复用现有实现。不得顺手修复无关问题，也不得覆盖用户已有改动。

## 4. 验

根据风险运行最小匹配验证：类型、Lint、单元测试、集成测试、构建、浏览器交互或部署后检查。未执行的验证必须明确标记。

## 5. 审

审查正确性、回归、安全、权限、数据暴露、前端状态、响应式和无关改动。结论必须有文件、命令或运行结果支撑。

## 6. 交

说明修改文件、用户可见变化、已验证、未验证、风险和下一步。不要把本地模拟、Fixture 或单账号检查描述成生产证据。

## 长期复利：捕获 → 提炼 → 验证 → 晋升 → 复用 → 淘汰

“读、规、做、验、审、交”负责完成当前任务；长期循环只捕获会改善后续任务的高信号知识。一次观察进入 Inbox，重复且有证据的项目规则进入 `AGENTS.md` 或 Playbook，稳定跨任务流程再创建 Skill。依赖、架构或官方行为变化后重新验证，失效内容及时淘汰，避免把知识库变成新的上下文负担。

每周 Scheduled 任务可以自动检查更新和整理候选，但默认只生成报告与晋升建议。当前项目、用户级 Skills、插件、账号和权限变化仍需人工确认。详见 [每周维护与知识复利](automations-and-compounding.md)。

## Context Headroom

- 保持主线程只承载需求、决策、边界和结论。
- 将详细规范放入 Skill 的 `references/`，仅在触发时读取。
- 大型脚本先看 `--help`，优先作为黑盒执行。
- 长日志只保留相关片段和摘要。
- 在阶段边界总结状态；长任务使用 `/status` 观察上下文，并在必要时 `/compact`。
- 保留足够上下文用于最终实现、验证和审查，不把窗口耗尽在探索阶段。
