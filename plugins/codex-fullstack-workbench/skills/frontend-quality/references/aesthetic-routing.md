# 前端审美路由与验收

`frontend-quality` 是所有视觉改动的质量门槛，不是固定风格发生器。先读项目已有组件、品牌和目标用户，再决定是否需要一个额外的审美专家。

## 先做一次设计判断

编码前用一句话写清楚：这是哪类页面，面向谁，核心气质是什么，沿用什么设计系统或视觉语言。没有这句话，就不应凭“高级感”自动套渐变、玻璃、巨型标题或三张等宽卡片。

## 何时只用 `frontend-quality`

- 修复组件、表单、状态、响应式、可访问性或性能。
- 应用内的仪表盘、表格、后台、向导、代码编辑器和高密度业务界面。
- 已有设计系统或 Figma 已经明确，任务只需忠实实现和浏览器验收。

这类任务优先使用既有设计系统和信息架构；审美的目标是清晰、可信和可用，不是做成营销页。

## 何时额外选择一个审美专家

以下场景可在 `frontend-quality` 之外，再选**一个**专家作为辅助：官网、营销页、作品集、品牌重塑、需要强叙事或关键转化页面。

| 已知条件 | 可选辅助能力 | 作用 |
| --- | --- | --- |
| 需要摆脱模板化视觉，并已有明确受众/气质 | Taste Skill 或 `frontend-design` | 形成具体艺术方向，避免通用 AI 风格 |
| 需要产品设计审查或高保真 UI 质量 | Impeccable 或 Product Design | 审查视觉一致性、交互与细节 |
| 有 Figma 源设计 | `figma:*` | 获取设计事实；它不是凭空决定审美的替代品 |
| 动效服务叙事、层级或反馈 | `gsap` 或现有动效能力 | 只实现有理由、可降级的动效 |

不要同时叠加多个审美专家。选择依据是它能否在当前任务中带来明确的视觉方向、实现质量或验收增益，而不是“安装了就要用”。

## 共同质量门槛

无论是否使用额外专家，交付前都应确认：

- 有明确的信息层级、字体、颜色、密度、圆角与阴影规则。
- loading、empty、error、disabled、focus、hover 与长内容状态可用。
- 没有无依据的 AI 紫渐变、过度玻璃、卡片套卡片、随机装饰或假产品截图。
- 动效只解释状态、空间或叙事，支持 `prefers-reduced-motion`，不会损害性能。
- 在真实浏览器检查窄屏手机、常见笔记本和宽屏；同时检查键盘、对比度和文案变长。
- 报告实际视口、浏览器和截图，而不是只凭代码说“好看”。
