# Requirements and Architecture

先把“想要什么”变成可以证明完成的条件，再选择最小架构。

## 工作流

1. 复述目标、用户、使用场景和不在范围内的内容。
2. 区分事实、假设、产品决策与技术决策。
3. 为正常路径、空状态、错误状态、权限和恢复路径写成功标准。
4. 映射受影响的 UI、API、数据、后台任务、监控和部署边界。
5. 比较 2–3 个真实可行方案，说明复杂度、可逆性和运维代价。
6. 选择最小可交付切片，为每一步指定验证和停止条件。
7. 对公开接口、迁移、权限扩大或不可逆动作先请求确认。

详细模板见 [references/decision-template.md](references/decision-template.md)。

## 约束

- 不用“可扩展”“企业级”等词代替具体机制。
- 不为假想需求提前引入服务、抽象或状态。
- 不把待确认的业务规则偷偷固化到代码方案中。
- 架构图必须能对应到文件、接口或运行组件。

## 输出

输出一份可审查的简短方案：目标、非目标、成功标准、方案、影响面、风险、验证和开放问题。
