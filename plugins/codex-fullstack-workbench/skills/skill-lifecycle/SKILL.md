# Skill Lifecycle

低频不等于低价值，没用过也不等于应该安装。先确认真实能力缺口，再在“直接完成、复用现有 Skill、安装第三方 Skill、创建自己的 Skill”之间选择成本最低且可信的方案。

## 工作流

1. 用具体例子定义任务、触发语句、频率、风险和期望输出，并读取插件根目录 [capability-routing-policy.json](../../assets/capability-routing-policy.json) 评估净收益。
2. 检查当前已安装和系统自带能力，避免为已有能力重复安装。
3. 需要发现能力时，优先使用可用的 `find-skills`、插件目录或 `npx skills find <query>`；搜索前先提炼具体关键词。
4. 不根据搜索排名直接推荐。读取候选 Skill 的完整 `SKILL.md`、脚本、来源和许可证，按 [references/evaluation-checklist.md](references/evaluation-checklist.md) 比较。
5. 展示候选的能力增量、重叠、上下文成本、网络/写权限、安装位置和验证方式；得到用户确认后才安装。
6. 安装后开启新任务，用一个无敏感数据的真实小任务验证发现、触发、输出和权限。
7. 没有可信候选，且流程会重复或包含非显然的领域知识时，调用可用的 `skill-creator` 创建项目级 Skill。
8. 创建后运行官方验证器，并用未泄露预期答案的真实样例迭代；不要因为校验通过就宣称工作流有效。
9. 用户要求定期更新时，读取 [references/weekly-maintenance.md](references/weekly-maintenance.md)：默认每周自动审计、Diff 和验证，不静默覆盖；只有显式启用后才在隔离 Worktree 暂存可信的项目级候选。
10. 发现重复纠错、有效技巧或稳定工作流时，读取 [references/knowledge-compounding.md](references/knowledge-compounding.md)，按“捕获、提炼、验证、晋升、复用、淘汰”处理，而不是保存全部聊天。

## 安装原则

- 优先项目级安装；只有多个项目长期需要时才考虑全局安装。
- `npx skills add ... -g -y` 同时意味着全局写入和跳过确认，不得默认使用。
- 安装量、Stars 和作者知名度只是信号，不能替代源码、权限与维护状态审查。
- 第三方 Skill 可能包含 Shell、网络和外部服务指令，必须像代码依赖一样审查。
- 同类能力保留一个主 Skill；有明确差异时才允许共存。

## 创建原则

- 一次性、常规且 Codex 已能稳定完成的任务不需要 Skill。
- 适合创建的内容包括稳定重复流程、组织专有规则、脆弱操作顺序、固定验证门禁和可复用脚本。
- 使用 `skill-creator` 的初始化、编辑、验证和迭代流程，不手写不完整脚手架。
- 主 `SKILL.md` 只保留触发与流程；细节放进一层 `references/`，确定性操作放进 `scripts/`。
- 不复制来源和许可证不明的第三方 Skill 内容。

## 更新与知识复利原则

- 自动化默认负责发现、比较、验证和报告，不自动扩大权限或覆盖当前有效配置。
- Marketplace 刷新、插件更新、账号重新授权和 Skill 文件替换是不同动作，分别审查。
- 单次经验只进入候选 Inbox；没有适用范围和验证证据，不晋升为规则或 Skill。
- 项目规则进入最近的 `AGENTS.md`，可复用工作流进入 Skill，需要实时数据或外部动作时使用插件/MCP。
- 每周复查过期来源、冲突和无增益内容；失效经验应淘汰，避免上下文持续膨胀。

## 输出

给出：能力缺口、选择结论、候选比较、权限与来源、安装/创建计划、验证结果、维护或卸载方式。定期维护还应给出版本 Diff、风险、回滚和是否需要人工晋升；知识复利应给出证据、适用范围和推荐载体。明确区分“未使用过”“未验证”和“没有价值”。
